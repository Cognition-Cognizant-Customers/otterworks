# Risk Register

One entry per unit in `analysis/WAVE_PLAN.md`. "What breaks" is the failure mode on the
live perpetual tenant `t-main.otterworks.app` (which tracks `main` via
`.github/workflows/cd-tenant.yml`) **if a wrong change reaches `main`** — every unit is
verified on its own `demo-<id>` tenant first, so this is the residual risk after the
unit's gates, not the expected path.

Rollback baseline for all units: `main` is only ever changed by merging the unit's PR, so
the universal rollback is `git revert` of the merge commit on `main`; cd-tenant then
redeploys `t-main` from the reverted `main` automatically. If `t-main` is stuck mid-rollout,
the only additional lever is `helm rollback` of the affected release to its previous
revision — `t-main` must never be image-pinned, checked in, or overridden
(`deploy-tenant.sh --image-tag` / `BUG_IMAGE_TAG_<service>` are for `demo-<id>` /
`workshop-<id>` tenants only, per `AGENTS.md`). Per-unit rows below note anything beyond
that baseline (data/schema, licensing, routing).

## Wave 1

| Unit | What breaks on `t-main` if wrong | How it is detected | Rollback |
|---|---|---|---|
| 1.1 Cross-cutting gate repair | Nothing at runtime — the unit touches `Makefile`, `ci.yml`, `angular.json`, jest/coveragerc thresholds only. Worst case is *pipeline* breakage: newly-real gates (admin-dashboard lint/test, executed api-flow job) start failing on `main`, blocking all subsequent merges. | The failing CI jobs themselves: `admin-dashboard`, `api-flow-tests`, `collab-service`, `search-service` jobs in `.github/workflows/ci.yml` turn red on the PR. No Grafana signal — no deployed artifact changes. | `git revert` on `main`; no tenant redeploy needed (no image changes). If only one gate is wrongly strict, revert that hunk rather than the whole unit. |
| 1.2 report-service rewrite | Report generation (PDF/XLSX) fails or produces wrong output for every tenant flow that hits `/api/.../reports` through the gateway; its own Postgres DB (`otterworks_reports`) schema may be migrated incompatibly. | CI: `report-service` job (ci.yml 320–335) and `tests/api/test_audit_analytics_report_flow.py` (executed in the `api-flow-tests` job after unit 1.1). Live: Grafana `observability/grafana/dashboards/service-detail.json` with `$service=report-service` (Error Rate 5xx, P99 Latency panels) and `incident-overview.json` "All Services - 5xx Error Rate". | Revert on `main` (cd-tenant redeploys `t-main`); `helm rollback` of the report-service release if the rollout is stuck. Schema risk: rewrite must ship reversible migrations against `otterworks_reports`; rollback plan includes running the down-migration before the old image serves. iText 5 removal is one-way by policy (AGPL) — rollback restores the old image but the license exposure returns, so treat rollback as temporary. |
| 1.3 legacy-portal replatform | Low blast radius on `t-main`: legacy-portal is not in the root `docker-compose.yml` today and nothing calls it. Wrong integration could break the *shared* Helm deploy (`scripts/deploy-tenant.sh`) for all services if the chart change is malformed, or fail the H2→Postgres profile switch and crash-loop the new pod. | CI: `legacy-portal` job (ci.yml 339–353) plus the image-build step added in-unit; `infrastructure` / `demo-platform` jobs for chart/compose syntax. Live: Grafana `otterworks-overview.json` "Service Health Grid" / "Services Down" shows the crash-looping pod; `service-detail.json` for the new service. | Revert on `main`. Because the unit *adds* a deployable, rollback is removal: `helm` uninstall of the legacy-portal release in the tenant namespace (or redeploy from reverted `main`, which no longer includes it). No shared data to unwind — it gets its own DB/profile. |
| 1.4 admin-dashboard refactor | Admin login breaks: replacing the client-side mock (`src/app/core/services/auth.service.ts`) with the real `POST /api/v1/admin/auth/login` fails if the backend contract is wrong — admins locked out of the dashboard on `t-main`. | CI: `admin-dashboard` job (now fail-capable after 1.1: lint, test, prod build). Runtime detection is browser-side, so Grafana coverage is indirect: `service-detail.json` with `$service=api-gateway` shows 401/4xx spikes on `/api/v1/admin/auth/*` in "Error Breakdown by Status Code"; the login regression itself is caught pre-merge by the seeded-admin login check on the unit's `demo-<id>` tenant. | Revert on `main` (cd-tenant redeploys); `helm rollback` of the admin-dashboard release if stuck. No data or schema involved (static SPA). |
| 1.5 file-service toolchain pin | Effectively nothing behavioral — the unit pins the Rust toolchain/base image. The risk is a *build* difference: a pinned-version compile or clippy divergence producing a subtly different (or unbuildable) binary. | CI: `file-service` job (ci.yml 117–132: fmt, clippy `-D warnings`, `cargo test`, release build) on the pinned toolchain; `tests/api/test_file_flow.py`. Live: `service-detail.json` `$service=file-service` error/latency panels; `business-metrics.json` "Files Uploaded (24h)" flatlining. | Revert the pin on `main` (cd-tenant redeploys); `helm rollback` of the file-service release if a bad image shipped. |

## Wave 3

| Unit | What breaks on `t-main` if wrong | How it is detected | Rollback |
|---|---|---|---|
| 3.1 api-gateway updates | **Total outage class.** Every request from both frontends transits the gateway; a bad route/config change 404s or 502s the entire platform for all users of `t-main` at once. | CI: `api-gateway` job (go vet, `go test -race`, build, coverage floor); the **full** ten-module `make test-api-flows` run in the `api-flow-tests` job — every flow crosses the gateway. Live: `otterworks-overview.json` "Total Request Rate" cliff + "Overall Error Rate" spike + "Error Rate by Service"; `incident-overview.json` "Active Alert Count" (Prometheus `observability/prometheus/alerts.yml`). | Revert on `main` (cd-tenant redeploys); `helm rollback` of the api-gateway release if stuck. Stateless proxy — no data to unwind; rollback is complete once the old image is serving. |
| 3.2 auth-service hardening | If the JaCoCo-only change accidentally alters runtime behavior (it must not): JWT issuance/validation breaks and **every authenticated call in the estate** fails — all services share `JWT_SECRET` and trust its tokens. | CI: `auth-service` job (`gradle check` incl. the new coverage verification); `tests/api/test_auth_flow.py` + `test_document_flow.py` (authenticated flow). Live: `otterworks-overview.json` "Overall Error Rate" (401 storm shows as gateway 4xx/5xx mix); `service-detail.json` `$service=auth-service` "Error Breakdown by Status Code". | Revert on `main` (cd-tenant redeploys); `helm rollback` of the auth-service release if stuck. Postgres schema untouched by this unit (build-config change only) — enforce "no `src/main` changes" in review to keep rollback trivial. |
| 3.3 legacy-portal decomposition | New gateway routes for the three extracted contexts (announcements, user-preferences, feedback) misroute or shadow existing paths — shared-path blast radius identical to 3.1 for any colliding route; the extracted services can also crash independently (contained). | CI: `api-gateway` job (routing change) + the per-context CI jobs added in-unit + the Wave 1.3 flow tests; full `make test-api-flows`. Live: `otterworks-overview.json` "Request Rate by Service" / "Error Rate by Service" for the new services; "Service Health Grid" for crash-loops. | Revert on `main`; the monolithic Wave-1.3 legacy-portal remains deployable, so rollback = remove the new releases + restore the pre-split routing (single revert commit). Data migrated out to per-context stores must ship with a documented reverse-ETL or be dual-written until the unit is proven. |

## Units not fully verifiable on an ephemeral tenant

Per `AGENTS.md`, **SNS/SQS eventing is disabled for tenants** ("SNS/SQS eventing is
disabled for tenants to avoid cross-tenant queue consumers"). Any behavior that runs
through SNS publish or SQS consumption therefore cannot be exercised on the unit's
`demo-<id>` tenant and is verified only after merge, on `t-main` (where eventing is
live), with the Grafana panels above as the detection net:

| Unit | Unverifiable path on `demo-<id>` | Residual verification |
|---|---|---|
| 2.1 search-service | The rewritten SQS consumer (`app/services/sqs_consumer.py` successor) — event-driven indexing of new documents/files. On the tenant, only synchronous query/suggest APIs and the contract test can run; index freshness cannot. | Post-merge watch on `t-main`: `business-metrics.json` "Documents Created (24h)" vs `otterworks-overview.json` "Search Queries (24h)" divergence; a manually triggered `tests/api/test_side_effect_flow.py` run against `t-main`'s gateway (read-only assertions only — no bug injection on `t-main`). |
| 2.2 analytics-service | SQS ingestion into the analytics store (`build.sbt` line 36 SQS dependency). Tenant verification covers only the HTTP surface report-service calls. | Post-merge watch on `t-main`: `service-detail.json` `$service=analytics-service`; staleness visible as flat analytics-derived panels in report output. |
| 1.5 file-service | SNS publish on upload/share (`SNS_TOPIC_ARN`) — downstream fanout to search/notification/audit is invisible on a tenant. Toolchain pin makes regression unlikely, but the publish path is still unexercised. | Post-merge: `test_side_effect_flow.py` against `t-main`; `otterworks-overview.json` "Notifications Sent (24h)" / "Audit Events (24h)". |
| 1.2 report-service | Its own API is synchronous and fully tenant-verifiable, **but** the audit/analytics data it reports on is event-fed; on a tenant those upstream stores are empty/stale, so report *content* correctness is only spot-checkable, not end-to-end verifiable. | Post-merge: run `test_audit_analytics_report_flow.py` against `t-main` and diff a golden report; `service-detail.json` `$service=report-service`. |

Consumers that are **not units** but sit on the disabled event path (notification-service
`SqsConsumer.kt`, audit-service `SnsConsumer.cs`, document-service SNS publish) are
unchanged by this plan; if any later unit touches them, it inherits the same limitation.

All post-merge verification on `t-main` is **observational only** — no chaos flags, bug
injection, or config overrides on `t-main` (prohibited by `AGENTS.md`).
